# QwenLLM: протокол и дизайн сравнения

## Два исследовательских вопроса

**Основной вопрос:** как различаются покрытие, mutation score, число тестов и
сходство спектров выполнения у результатов EvoSuite, Randoop и QwenLLM?

Для основной сравнительной таблицы заранее зафиксированы конфигурации:

| Инструмент | Условие получения набора | Смысл budgetSec |
|---|---|---|
| EvoSuite 1.2.0 | search budget 120 секунд | внутренний бюджет поиска |
| Randoop 4.3.3 | time limit 120 секунд | внутренний бюджет генерации |
| QwenLLM | цель — 10 принятых JUnit-сценариев; при пределе сохраняется частичный набор | 1800 секунд — защитный предел |

120 секунд для исходных инструментов выбраны как максимальный уже имеющийся
уровень исследования. Это сравнение качества результатов **явно указанных
конфигураций**. Для него одинаковое фактическое время не требуется. Фактическое
время и стоимость получения результата сохраняются как дополнительные сведения.

**Вторичный вопрос:** как качество меняется при бюджетах 30/60/120 секунд?
Он относится к EvoSuite и Randoop. Qwen не включается в эти временные кривые:
его остановка определяется числом принятых тестов.

`experiment.toml` задаёт общие классы и seed, `[tool_budgets]` — отдельный
защитный лимит Qwen, `[comparison.reference_budgets]` — конфигурации основного
сравнения. Папка `QwenLLM/<Class>/1800/` означает этот предел, а не обязательную
генерацию в течение 30 минут.

## Реализация QwenLLM

QwenLLM — авторский генератор `qwen-result-quota-v3`, использующий
Qwen2.5-Coder 3B Instruct Q4_K_M через Ollama 0.33.3. Он реализует генерацию,
валидацию и ограниченное исправление. Это самостоятельный baseline; называть
его ChatUniTest или переносить на него результаты статьи ChatUniTest нельзя.

Машина: Intel Core i5-13500H, около 16 ГБ ОЗУ, Intel Iris Xe, CPU inference.
Модель выбрана с учётом этой конфигурации. Модель, квантование, runtime,
шаблон запроса, sampling и правила принятия вместе образуют исследуемый инструмент.
Digest модели закреплён в `llm.toml`; несовпадение останавливает запуск.

### Правила одного повторения

1. Собрать production-классы Java 17. Получить classpath без классов ручных и
   сгенерированных тестов. Загрузить модель в память; записать время прогрева
   отдельно от времени серии.
2. Начать секундомер и новую последовательность запросов для class/seed.
3. Начальный запрос содержит только исходник целевого класса, фиксированное
   задание и имя нового тестового класса. Другие проектные тесты, JaCoCo/PIT,
   ручные oracle и результаты других генераторов модели не передаются.
4. Запрашивать один JUnit 4 класс с **ровно одним @Test-методом**. Метод может
   содержать несколько assertions и входных примеров; единица учёта — JUnit-метод.
   Параметры: temperature 0.7, top_p 0.9, context 8192, output limit 1024,
   6 CPU threads. Seed кандидата = seed серии + номер кандидата − 1.
5. Сохранить запрос и полный исходный поток ответа. Единственная механическая
   подготовка кода: убрать Markdown fences и обеспечить импорты JUnit 4,
   целевого класса и его вложенных типов. Тела методов и assertions адаптер
   не редактирует.
6. Отклонять незавершённый ответ, неверный пакет/имя, отсутствие assertions,
   отключённые тесты и число @Test, отличное от одного.
7. Компилировать javac --release 17. Дважды выполнить JUnitCore в новых JVM;
   каждый запуск должен успешно выполнить ровно один тест. Проверки включены
   во время серии. Только затем включить кандидат в итоговые Java-исходники.
8. После неудачи разрешены до двух последовательных repair-запросов с
   предыдущим ответом и диагностикой компилятора/JUnit. Полные repair-prompts
   сохраняются. После успеха или исчерпания этой цепочки начать новый запрос
   с исходника. Покрытие и mutation score не используются для исправления.
9. Остановиться после 10 принятых тестов. Дополнительные защитные ограничения:
   100 запросов и 1800 секунд на серию. При срабатывании ограничения сохранить
   весь уже полученный результат и указать причину остановки. Незавершённый
   последний ответ не принимается. Время закрытия сокета и записи JSON может
   дать небольшое превышение предела, видимое в фактическом времени.
10. Оценить весь принятый набор обычным Gradle/JUnit 4, JaCoCo 0.8.12 и PIT с
    теми же target class, mutators и параметрами, что и исходные генераторы.

Число 10 у Qwen задано правилом остановки и не является самостоятельным
показателем производительности или естественного объёма выдачи модели.
Качество оценивается по покрытию, PIT и спектрам. Допускаются
повторяющиеся сценарии: их избыточность отражается в покрытии и спектрах.
Ручного удаления неудачных assertions, выбора лучшего seed по PIT или
редактирования принятых тестов нет.

## Данные и агрегация

- В исходной части: 2 × 4 × 3 × 10 = 240 серий.
- Полный план Qwen: 4 класса × 10 seed = 40 серий с единой квотой,
  без трёх уровней временного бюджета.
- Проверка интеграции с одним seed — отдельная малая выборка. Для PricingEngine
  после пустого первого запуска дополнительно запущен seed 202 с тем же
  протоколом. Обе серии сохраняются, включая EMPTY. Это адаптивное расширение
  проверки работоспособности, а не заранее сбалансированный эксперимент.
  Размер каждой выборки указывается в таблицах; она не выдаётся за 10 повторений.
- Основные сводки выбирают reference-конфигурацию каждого инструмента и
  сравнивают показатели по каждому классу. Интегральные значения усредняются
  по классам с одинаковым весом, а не по числу тестов.
- Временные графики используют полные данные EvoSuite/Randoop по трём бюджетам.
- Для спектров основной пары Qwen–другой инструмент сопоставляются class/run/seed
  при **разных** reference budgets. В CSV явно сохраняются
  `tool_a_budget_sec` и `tool_b_budget_sec`. Отсутствующее повторение
  не подменяется измеренным нулевым сходством.
- `llm-run.json` и `audit/` сохраняют fingerprint, source hash, все ответы,
  диагностику, phase/repairDepth и причину остановки. `generation_runs.csv`
  дополняется новыми строками.
- `llm_generation_outcomes.csv` включает каждую серию, в том числе EMPTY/FAIL,
  число принятых и отклонённых кандидатов, repair-запросов и фактическое время.
  `completedOutputTokens` учитывает ответы с финальной статистикой Ollama;
  токены прерванных ответов отдельно не оценены, raw-поток сохранён.
- В `quality_runs` EMPTY имеет отсутствующие метрики, а не фиктивный PIT=0.
  Условные средние качества публикуются вместе с долей непустых серий и
  достижением квоты. Ошибки инфраструктуры отделяются от неудачной генерации.
- Доверительный интервал для одного повторения не оценивается.

### Сохранённые пилоты

Первоначальные короткие прогоны сохранены для аудита:

- v1, без repair: 4 EMPTY при 120 секундах; исходники/ответы в
  `src/generatedTest/diagnostic-v1/`, данные в `reports/data/diagnostic-v1/`.
- v2, с repair, ещё с ограничением 120 секунд: один непустой набор из четырёх;
  исходники в `src/generatedTest/pilot-v2/`, данные в `reports/data/pilot-v2/`.
  Для LIS получены 14 прошедших тестов, 93,33% line, 90% branch, 9/9 killed.
- Снимки адаптеров v1/v2 находятся в `docs/archive/`. После уточнения цели
  исследования v3 использует остановку по результату и отдельный защитный лимит.
  Пилоты не смешиваются с основной конфигурацией v3.

Разработка протокола на этих учебных объектах ограничивает независимость оценки.
Изменение модели, prompt или stopping rule требует отдельной версии и данных.

## Запуск

Из корня проекта в PowerShell:

```powershell
.\scripts\setup_llm.ps1
$env:JAVA_HOME = 'C:/Users/user/.jdks/jbr-17.0.14'
$env:PATH = "$env:JAVA_HOME/bin;$env:PATH"
uv sync --project scripts --locked

# Один повтор для каждого класса; бюджет Qwen берётся из его отдельной настройки.
uv run --project scripts python scripts/generate_test_suites.py --tools QwenLLM --seeds 101
uv run --project scripts python scripts/analyze_test_quality.py --tools QwenLLM
uv run --project scripts python scripts/summarize_llm_runs.py
uv run --project scripts python scripts/analyze_trace_similarity.py --tools QwenLLM --collect-only
uv run --project scripts python scripts/analyze_trace_similarity.py --tools EvoSuite,QwenLLM --skip-collect
uv run --project scripts python scripts/analyze_trace_similarity.py --tools Randoop,QwenLLM --skip-collect
uv run --project scripts python scripts/build_report_assets.py --output-dir reports/generated/three-tools
```

Для полной независимой серии из 40 повторений можно выбрать новый корень:

```powershell
uv run --project scripts python scripts/generate_test_suites.py --tools QwenLLM --output-root src/generatedTest/main-experiment
uv run --project scripts python scripts/analyze_test_quality.py --tools QwenLLM --generated-tests-root src/generatedTest/main-experiment
uv run --project scripts python scripts/summarize_llm_runs.py --generated-tests-root src/generatedTest/main-experiment
uv run --project scripts python scripts/analyze_trace_similarity.py --tools QwenLLM --collect-only --generated-tests src/generatedTest/main-experiment
```

Эти команды заменяют рабочие сводки Qwen данными новой серии, сохраняя
исторические данные EvoSuite/Randoop. Затем повторите два сравнения трасс и
построение графиков из первого блока. Для независимого каталога сводок можно
задать `--report-root`; у коллектора трасс — `--traces-dir` и `--out`.
Явный `--budgets` переопределяет настройки инструмента и предназначен для
отдельных экспериментальных конфигураций. Новые запуски создают новые run.

Portable runtime и веса находятся в `tools/ollama/` и `tools/ollama-models/`,
исключены из Git. Сервер слушает `127.0.0.1:11435`; ключи внешних API не нужны.
После перезагрузки: `./scripts/setup_llm.ps1 -SkipModelPull`.
PID запущенного серверного процесса хранится в `tools/ollama/server.pid`.

## Ограничения интерпретации

Repair проверяет соответствие текущей реализации: исправленная моделью
ожидаемая величина не является независимым доказательством правильности кода.
Assertions могут быть слабыми; для этого измеряется PIT. Два успешных запуска
снижают, но не устраняют риск flaky tests. Историческое удаление EvoSuite
scaffolding и учёт только выбранного top-level class в JaCoCo сохранены.

Одинаковый seed не создаёт одинаковую случайность у разных генераторов и
не гарантирует побитово одинаковые ответы LLM. На скорость влияют CPU,
версия runtime, прогрев и кэширование префикса. Четыре небольших класса и
возможное присутствие похожего кода в обучающих данных ограничивают обобщение.
Выводы относятся к данной связке QwenLLM, модели 3B и правилам получения набора.
Для сравнения эффективности по затраченному времени нужен отдельный дизайн.
